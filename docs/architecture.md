# Drudge 架构与产品边界

本文是 Drudge 的产品与架构基线。它回答四个问题：系统为什么存在、当前怎样运行、哪些原则不能被普通迭代改变、哪些实现可以演进。

实现细节仍以当前源码和测试为准。发现本文与源码不一致时，应先判断是文档漂移还是未经记录的架构变化，再修正其中一方。

## 1. 产品核心

Drudge 的核心目标是：

> 持续获取实时财经信息，保留关键事实，使用 AI 将其整理成可快速阅读的高信息密度内容，并可靠地主动推送给用户。

“有新闻文件”“有图谱节点”或“接口返回 200”都不是最终价值。完整链路必须让用户及时收到忠实、可读、可追溯的信息。

### 1.1 不可由 AI 自行改变的原则

- 主链路包含采集、处理、总结和主动推送，不能只保留其中一段。
- 数字、时间、主体、来源、事件、方向和可用原文链接属于基本信息量。允许去重、聚合、分组和改写，不允许仅为缩短消息而静默删除关键事实。
- 输出必须区分来源事实与模型推断；没有依据时不补写背景、因果或投资结论。
- 失败必须可见、可追踪、可重试，不能把局部失败包装成完整成功。
- 价格与能力合适即可，模型提供商不是产品绑定；模型切换不能改变业务输出契约。
- 系统服务自身的信息消费，不负责自动交易或替用户作投资决定。
- 优先选择简单且可以实际运行的方案，不建设与当前目标无关的通用平台。

### 1.2 三层变更权限

| 层级       | 内容                                                           | AI 权限                                  |
| ---------- | -------------------------------------------------------------- | ---------------------------------------- |
| 产品核心   | 上述目的、信息保留、事实边界、主动推送                         | 只能由用户明确决定                       |
| 受保护架构 | 数据契约、消费位点、Neo4j schema、外部 API、调度和部署拓扑     | 可提出方案；变更前需说明迁移与回滚并确认 |
| 实现细节   | 函数拆分、局部组件、提示词内部实现、测试辅助、无行为变化的整理 | 可在当前任务范围内最小演进               |

Neo4j、Web UI 和婷子机器人目前属于“受保护的当前能力”，不是已经确认的永久产品目的。AI 不能自行移除，也不应把它们设计成不可替换。

## 2. 当前系统全景

```text
Futu API             AWTMT API
    |                     |
    +----------+----------+
               |
      ingest-worker（每分钟）
              |
              v
      data/news/<source>_<time>.json
              |
              v
      graph-worker（每分钟）
       |       |        |
       |       |        +--> data/news/failed/
       |       +----------> data/news/.processed/
       v
          Neo4j
              |
              v
    web-app + web-scheduler
       |       |        |
       |       |        +--> 图谱/统计页面
       |       +----------> Level 1 扫描与周期总结
       v
  钉钉企业机器人单聊
       |             |
       |             +--> H5 完整详情
       +----------------> 紧凑图片摘要
```

### 2.1 Workspace 责任

#### `packages/ingest-worker`

- 通过 `FutuLiveService` 和 `AwtmtLiveService` 并行拉取两个源。
- 以各来源最近一次新闻 ID 为边界，只保存新内容。
- 将内容按来源分组，写入 `data/news/<source>_<timestamp>.json`。
- 提供健康、查询、手动采集、调度和数据清理 API。
- 采集或落盘失败时可通过告警 Webhook 通知。

它不调用图谱抽取，也不负责业务摘要。

#### `packages/graph-worker`

- 只扫描 `futu_live_*.json` 与 `awtmt_live_*.json`。
- 优先处理修改时间较新的未消费文件，避免历史积压阻塞实时内容。
- 调用 LLM 提取新闻级别、事件、公司、人物、机构、地点和业务关系。
- 使用 `MERGE` 写入 Neo4j，并建立系统关系和同新闻共现推断关系。
- 保存单条新闻处理失败证据，提供查询、重试和数据库 CLI。
- 对成功消费的文件写 `.processed` 标记。

它不直接抓取外部新闻源。

#### `packages/web-app`

- 直接读取 Neo4j，提供新闻、实体、网络、统计和展示页面。
- 执行 Level 1 新闻扫描、小时/日/周总结和消息编排。
- 先持久化完整简报，再通过钉钉企业机器人向显式指定用户发送图片摘要和 H5 详情入口。
- 提供婷子机器人测试入口。
- 总结报告页支持按北京时间选择范围、生成和复制全文，并可显式选择推送；实时监控页读取 worker 健康接口、图谱数据库检测与当前扫描状态。
- 新闻浏览支持搜索、筛选和完整详情；图谱可双击节点查询其关联，查询失败与部分结果会明确提示；统计页包含真实关系类型分布。概览只展示调度 API 声明的四类已实现任务，历史占位触发器继续保留在后端。
- `web-scheduler` 是独立 PM2 进程，通过 HTTP 调用 Web API，不嵌入 Next.js 进程。

#### `shared/common`

- 唯一的根环境变量加载和三类运行配置构造器。
- 北京时区与时间格式。
- 节点、事件、关系等公共枚举。
- LLM 提供商与通知辅助。

公共包只收纳已经跨包复用的稳定能力，不承担业务流程编排。

## 3. 端到端数据契约

### 3.1 原始采集记录

落盘记录的稳定核心字段为：

| 字段                            | 含义                              |
| ------------------------------- | --------------------------------- |
| `id`                            | 来源内新闻 ID；去重和图谱新闻主键 |
| `title`                         | 标题                              |
| `content`                       | 正文或快讯内容                    |
| `source`                        | `futu_live` 或 `awtmt_live`       |
| `time`                          | 来源时间，当前采集层使用数值      |
| `url`                           | 可选原文链接                      |
| `author`、`category`、`summary` | 来源存在时保留的可选信息          |

文件当前是 JSON 数组。graph-worker 兼容含 `data`、`list` 或 `news` 数组的对象，但这只是输入兼容能力，不应成为新增格式的理由。

### 3.2 消费位点

对 `data/news/x.json`，处理标记为：

```text
data/news/.processed/x.json.processed
```

只有标记文件的修改时间不早于原新闻文件，才视为已处理。删除标记会触发重放；修改原文件会使旧标记失效。

当前文件级规则是：一批新闻成功数大于失败数时标记整个文件。此行为涉及重放和遗漏风险，修改前必须设计兼容与迁移，不可当普通重构。

### 3.3 失败证据

单条失败新闻保存在 `FAILED_NEWS_DIRECTORY`，默认对应 `data/news/failed/`。记录包含原始 `newsItem`、错误、时间、来源和标题，可通过 Graph CLI 重试。

失败文件只有在对应新闻重试成功后才会删除。任何按天数清理失败文件的命令都是业务数据删除，不是常规维护。

### 3.4 时间

- 数据库存储和服务间时间优先使用 UTC ISO 8601。
- 调度与用户展示使用 `Asia/Shanghai`。
- 原始时间尽可能保留在 `raw_time`，便于排查来源解析。
- 不允许仅通过字符串截取假定时区。

## 4. Neo4j 模型

核心节点为 `News`、`Event`、`Company`、`Person`、`Organization`、`Location`。新闻 ID、事件 ID 和各实体名称是当前合并与唯一性主键。

关系分三类：

1. 新闻归属关系：`DESCRIBES`、`INVOLVES`、`MENTIONS`、`LOCATED_AT`。
2. LLM 提取的业务关系：如 `WORKS_FOR`、`ACQUIRES`、`SUPPLIES`、`REGULATED_BY`。
3. 同新闻共现推断关系：人物到公司、实体到地点，带 `inferred=true` 和来源新闻。

精确字段、枚举、索引和变更规则见 [数据库结构](../packages/graph-worker/DATABASE_SCHEMA.md)。

## 5. 调度与消息

| 进程            | 当前频率           | 有效行为                                 |
| --------------- | ------------------ | ---------------------------------------- |
| `ingest-worker` | 每分钟             | 拉取两个来源并落盘新增新闻               |
| `graph-worker`  | 每分钟             | 扫描并处理未消费文件；上一轮未结束则跳过 |
| `web-scheduler` | 每 5 分钟          | 扫描新的 Level 1 新闻并聚合通知          |
| `web-scheduler` | 11:05–22:05 每小时 | 生成上一完整小时总结并通知               |
| `web-scheduler` | 每天 10:05         | 生成隔夜总结并通知                       |
| `web-scheduler` | 周五 16:05         | 生成七天周报并通知                       |

当前 `web-scheduler` 还注册了若干只返回成功、没有业务行为的占位触发器。它们不是可扩展架构承诺，见“已知结构债务”。

### 5.1 消息内容原则

通知格式可以演进，目标是在手机聊天窗口中降低阅读成本，但必须遵守：

- 先给时间范围、新闻数量和重要级别，再给正文分组。
- 同主题可合并，但应保留最新时间、最大影响数字和差异信息。
- 消息首屏只显示固定尺寸图片摘要：最高权重的一条信息突出显示，另外两条紧凑排列，超过三条只提示剩余数量。
- H5 使用常驻目录与当前详情；低权重信息通过点击切换渐进披露，目录始终保留，全部条目均可访问。
- 图片可以截取用于扫读的文案，但完整简报不能截断、折叠成不可恢复的“其余 N 条”，也不能静默丢失基本信息量。
- 摘要、实体、历史背景与原文事实应有清楚层级。
- 发送失败不能被记作已发送；重试必须有明确上限。
- 展示格式与钉钉传输应分层，避免每个调用点自行拼接一套消息。
- 主动推送必须显式指定收件人；通知默认关闭，收件人为空或不合法时不发送。
- 当前只允许一个可配置收件人。未来如扩展多人，只能使用显式白名单逐人投递，不得增加默认全员、默认群聊或隐式广播分支。
- 简报 URL 使用不可遍历的 128 位标识，但当前没有用户登录；消息或链接被人工转发后仍可访问，因此不得放入密钥、私人正文或高敏感告警。
- 简报与工作台统一使用 `drudge.microzj.com`。按用户要求当前不加账号密码认证，页面与 API 直接访问；工作台仍检查浏览器跨站操作。

简报数据契约、展示和启用流程见[钉钉简报手册](dingtalk-briefing.md)。收件人决策见[显式收件人决策记录](decisions/2026-09-01-dingtalk-explicit-recipients.md)，展示方案见[图片摘要与 H5 决策记录](decisions/2026-09-03-image-briefing-h5.md)。

## 6. 对外接口边界

- `POST /trigger/fetch-news`
- `POST /trigger/fetch-batch`
- `GET /api/news/list`
- `GET /api/news/count`
- `GET /api/news/status`
- `POST /api/news/clean`：删除能力，需独立授权
- `GET /api/scheduler/status`
- `POST /api/scheduler/trigger`

### 6.2 Graph Worker

- `GET /`、`GET /health`
- `POST /api/news/process`
- `POST /api/news/batch`
- `POST /api/news/status`
- `GET /api/stats`
- `GET /api/news`、`GET /api/news/:id`
- `GET /api/news/level/distribution`
- `GET /api/entities/search`
- `GET /api/entities/:name/relations`
- `GET /api/entities/popular`
- `GET /api/entities/:name/news`
- `GET /api/system/status`

### 6.3 Web App

- 新闻：`/api/news`、`/api/news/search`
- 图谱：`/api/graph/data`、统计、热门、机构、实体搜索和邻域
- 业务动作：`/api/scan`、`/api/summary`、`/api/scheduler`、`/api/tingzi`
- 公共简报：`/briefings/<id>`、`/briefings/<id>/image.svg`
- 只读监控：`GET /api/monitor`，检查同机 worker 的现有健康接口；数据库状态来自 graph-worker 的连接检测，无法取得该检测时返回未知。

简报和工作台共用 `drudge.microzj.com`，都由 Tide 的同一个 Web App 提供。按用户明确要求，入口声明为 `public/none`，工作台页面及 API 无需账号密码，应用不再按公网 Host 限制业务路由，也不依赖代理认证标记。工作台的扫描、AI 总结和推送接口因此可直接访问；浏览器跨站操作检查不属于身份认证，不能限制直接调用者。钉钉服务自身的 API 凭据、通知开关和显式收件人规则保留。域名决定见[统一入口记录](decisions/2026-09-05-unified-drudge-domain.md)，迁移及验收见[发布手册](deployment.md#12-工作台入口)。

接口的请求参数和响应以路由代码与测试快照为准。修改现有接口需要兼容性说明和测试，不能只更新本列表。

## 7. 配置与环境

- 根 `.env` 是唯一真实配置入口。
- `env.example` 是唯一模板，只能放占位值。
- 三个包通过 `@drudge/common` 构造配置，禁止各自再实现一套 dotenv 搜索顺序。
- 默认端口：ingest `39110`、graph `39111`、web `39112`。
- AI 主提供商、备用提供商和简单任务提供商均可配置。
- 通知关闭或没有显式收件人时应安全失败，不应调用外部发送接口或推进已发送状态。

环境变量的具体清单只维护在 `env.example` 和公共配置解析中；本文不复制第二份易漂移清单。

## 8. 代码、GitHub 与 PVE 的角色

```text
本地工作区：修改、测试、review
        |
        v
GitHub main：共享代码基线与审计记录
        |
        v
PVE：生产构建和运行同一 commit
```

生产不应直接修改源码。一次发布只有在本地、GitHub 和 PVE 指向同一目标提交，并且进程与健康检查通过后才算完成。

发布控制、批准、失败停止和回滚见 [发布手册](deployment.md)。

## 9. 已知结构债务

以下是当前源码事实，不是自动授权的改造清单：

1. `web-scheduler` 注册十类触发器，其中多类只是占位成功响应；调度表达式还与公共配置中的 `CRON_*` 字段并存，事实源未完全收敛。
2. Level 1 通知的 `lastScanTime` 与已处理 ID 只保存在 Web 进程内存中；重启后去重状态丢失。
3. 批量实体写入成功后，业务关系写入异常只记录日志，新闻结果仍可能被视为成功，存在“节点完整、关系不完整”的一致性风险。
4. Graph Worker 提供查询 API，而 Web App 也直接访问 Neo4j，查询责任和数据映射有重复。
5. 简报快照当前没有自动保留期；生产启用一段时间后需要根据实际体积决定清理规则，清理前必须先确认链接有效期。
6. Neo4j 约束和索引创建混在运行时初始化中；未来 schema 迁移需要独立版本和回滚机制。

处理债务时一次只解决一个明确问题，先补可复现测试和验收，不借机整体重写。

## 10. 尚待用户确认的产品决定

在用户明确回答前，采用最保守规则：

- 知识图谱是长期核心，还是当前用于结构化与查询的可替换实现？
- Web UI 是面向日常使用的产品界面，还是主要用于运维和查证？

前两项当前都保留并维护，但 AI 不得据此扩大投入，也不得自行删除。用户已确认复用现有企业机器人“牛长婷”作为主动推送通道；其收件人和展示边界按第 5 节执行，但机器人仍属于可替换的受保护架构能力，不是产品核心。
